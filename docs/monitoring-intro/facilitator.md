# 講師用ガイド

## 進め方

1つの完成済み監視スタックを説明するのではなく、各章の困りごとを先に問いかけます。「この確認が成功したら、何が分かるでしょうか」「それでも見逃す故障を1つ挙げてください」を、設定項目の説明より先に扱います。

前半 60〜90 分は準備と第 1〜4 章、後半 60〜90 分は第 5〜7 章と整理が目安です。第 1 章で停止・再起動を全員が体験できたことを確認してから、監視対象を広げます。

## 開催前に実機で確認する

- Windows の WSL 2 / Ubuntu で ZIP の展開とコピーができる
- 同じ Ubuntu を複数のターミナルで開ける
- Python 3.10 以降と sqlite3 モジュールが使える
- 18080 番を別のサービスが使っていない
- 正常時が 500 ミリ秒を十分下回る
- 第 1〜7 章を実機で通し、Ctrl+C と復旧操作を確認する
- 社内端末の制約や Windows 側のセキュリティー製品が作業に影響しない

[検証記録](./verification.md)は、教材作成環境での確認範囲です。受講者の Windows / WSL 環境まで検証済みという意味ではありません。

## 安全上の約束

実験対象は同梱のアプリと `.state/` の学習用ファイルだけです。監視先はループバックに固定しています。ポートを公開せず、実データ、認証情報、Webhook URL も使いません。監視通知はターミナル表示までです。

DB ファイルの退避は「SQLite を開けない故障」です。PostgreSQL サーバー停止や通信障害として説明しないでください。遅延も明示的な待ち時間であり、CPU や DB の性能劣化を再現したとは言いません。

各故障の解除方法を先に見せます。複数の故障を同時に入れず、前の故障が解消したことを確認して進めます。

## 成果物と評価

受講者から、次の短い記録を1つずつ集めます。

1. 正常・故障・復旧の CHECK
2. 200 でも内容不一致になる例
3. 応答時間のしきい値とタイムアウトの違い
4. ALERT と RECOVERY の出た条件
5. 事実・仮説・次の確認を分けた調査メモ
6. 監視自身の停止と、同一ホストの限界
7. 自分のサービスで最初に1つ足す監視

コマンドを再現できたかだけでなく、「成功しても何は分からないか」を言葉にできたかを確認します。

## 実装を読む場合の順番

最初は `monitor.py` の1回の確認と出力だけに注目します。次に繰り返し、内容の判定、時間の判定、通知状態、観測時刻を見ます。入力制限やファイル処理などの安全対策は、必要な場面で解説します。Python の構文講座にしなくても進行できます。

標準ライブラリーの HTTP サーバーは学習用です。本番で使う Web サーバー、監視サービス、認証、通知・当番設計は別の課題として扱います。
