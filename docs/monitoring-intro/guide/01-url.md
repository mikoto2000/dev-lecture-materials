# 1. まず URL が返事をするか確かめる

## 困りごと

アプリを起動しました。でも、プロセスが見えるだけでは HTTP の返事が返ってくるか分かりません。最初は「この URL が HTTP 200 を返すか」だけを確かめます。

## 小さな追加: 一回だけ確かめる

ターミナル A でアプリが動いている状態で、ターミナル B から実行します。

```bash
python3 monitor.py --path /health
```

`CHECK` の行で `ok` が true、HTTP の状態が 200 であることを確認します。実際の出力は JSON 形式です。以後、教材ではフィールドの意味を読み取ります。

- 時刻: いつ確認したか
- 状態: HTTP の返事が返ったか
- `ok`: 今回の条件を満たしたか
- 理由: 失敗した場合の手がかり

`/health` は決まった内容を返す、最も小さな確認用 URL です。監視スクリプトの中心は「リクエストを送る → 返事を読む → 条件と比べる」です。アプリの内部実装を全部読む必要はありません。

## 安全な故障: アプリだけを止める

**戻し方はターミナル A で `python3 app.py` を再実行することです。**

1. ターミナル A で Ctrl+C を押す
2. ターミナル B でもう一度確認する

```bash
python3 monitor.py --path /health
```

今回は `ok` が false となり、接続できなかった理由が出ます。確認コマンドが失敗の終了コードを返すのも意図した結果です。いつまでも待ち続ける必要はありません。

## 復旧

ターミナル A で再び起動します。

```bash
python3 app.py
```

ターミナル B で同じ条件で確認し、200 に戻ったことを確かめます。

```bash
python3 monitor.py --path /health
```

アプリを再起動した事実だけで復旧とせず、**最初に失敗した確認をもう一度成功させる**ところまで行います。

## 確かめた範囲

分かったのは、この Ubuntu からこの時点で `/health` の返事を受け取れたことです。DB が読めること、利用者の操作が成功すること、別の PC から到達できることは、まだ分かりません。

## チェックポイント

- 停止前、停止中、再起動後の3つの `CHECK` を比べる
- 「プロセスが動いている」と「HTTP 200 が返る」は何が違うか説明する
- 1回成功しただけでは、その後の停止を発見できない理由を考える
