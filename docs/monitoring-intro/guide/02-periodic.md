# 2. 人の代わりに、繰り返して確かめる

## 困りごと

1回ずつ手で実行していると、見ていない間の停止を発見できません。前章の確認を、時刻を残しながら繰り返します。

## 小さな追加: 間隔・上限・時刻

ターミナル B で実行します。

```bash
python3 monitor.py --path /health --count 30 --interval 2
```

最大 30 回確認し、各回が終わってから 2 秒待ちます。開始時刻ぴったりの 2 秒周期ではありません。処理にかかった時間も次の確認までの間隔に加わります。回数に上限があり、途中で Ctrl+C を押して止めることもできます。

確認結果には UTC の時刻が付きます。ログを比べるときも同じ時刻基準を使います。応答時間の測定には、時計の時刻補正の影響を受けにくい単調増加時計を使います。

この教材のスクリプトは、1回の HTTP 処理を別プロセスで行い、既定で 1 秒を超えたら打ち切ります。`--timeout` で変更でき、応答本文も 4096 バイトまでに制限します。OS によるプロセスの起動・終了の都合で小さな超過はあり、厳密なリアルタイム保証ではありません。

HTTP ライブラリーのソケットタイムアウトだけでは、少しずつ応答が届き続ける場合などに処理全体を制限できません。そのため、この教材は外側のプロセスにも待機上限を置いています。最初は「確認が進まなくても次へ進めるための制限」と捉えれば十分です。具体的な制限は配布資料の README で確認できます。

## 安全な故障: 見ている間に止める

**復旧はターミナル A で `python3 app.py` を再実行します。** 監視が終了してしまった場合は、ターミナル B でも同じ監視コマンドを再実行してください。

1. `CHECK` が数回成功するのを見る
2. ターミナル A で Ctrl+C を押してアプリだけ止める
3. 次の `CHECK` が失敗し、`ALERT` が出るのを見る
4. ターミナル A でアプリを再起動する
5. `CHECK` が成功し、`RECOVERY` が出るのを見る

この `ALERT` はターミナルへの表示です。メールや Slack に通知を届けたわけではありません。「異常を判定する」と「人に届く経路を用意する」は別の仕事です。通知先を増やす前に、ここで判定を確かめます。

## 復旧

アプリが動いており、監視結果が成功に戻ったことを確認します。監視は回数上限で終了します。続ける必要がある場合だけ再実行します。

## 確かめた範囲

1回の確認より、停止を発見できる時間帯が広がりました。ただし確認と確認の間に起きて戻った短い障害は見逃せます。監視プロセスが止まれば確認されません。

監視の終了コードは、途中で1回でも条件を満たさない確認があれば 1 になります。最後に復旧していても、実行全体は成功扱いになりません。いつ失敗し、いつ復旧したかは、`CHECK` と `ALERT` / `RECOVERY` の記録を読みます。

## チェックポイント

- 停止から最初の失敗表示まで、何秒程度かかったか
- `--interval 5` に変えると、発見の遅れと確認回数はどう変わるか
- 一人に知らせるなら、何を含めるべきか。「対象・時刻・条件・次の確認先」を挙げる
