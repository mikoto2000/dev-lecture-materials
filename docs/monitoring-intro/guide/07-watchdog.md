# 7. 監視が止まったときも、静かでよいだろうか

## 困りごと

ALERT が出ていません。正常なのでしょうか。それとも、監視プロセスが止まっているのでしょうか。「何も届かない」を成功扱いしないために、最後に確認した時刻を使います。

## 小さな追加: 最終観測が新しいか、別のコマンドで見る

監視は確認を1回終えるたび、`.state/last-check.json` を更新します。成功した回だけではありません。失敗した回も、監視が実行された証拠なので更新します。

書き込み途中を読み取ることを避けるため、一時ファイルを書いてから置き換えます。ターミナル B で、まず繰り返し確認を始めます。

```bash
python3 monitor.py --path /items/1 --expect-name monitoring-demo --count 60 --interval 2
```

ターミナル C では、別のコマンドで確認します。

```bash
python3 watchdog.py --max-age 5
```

最終観測が 5 秒以内なら、新しい観測があると報告します。**これは監視が最近確認したという意味で、アプリが正常という意味ではありません。** ファイルがない、壊れている、未来の時刻になっている場合も成功扱いしません。

5 秒はこの実験の例です。実運用では、監視間隔だけでなく、1回の確認の最大所要時間や書き込みの余裕を考慮します。境目で揺れる場合は最後の CHECK の時刻を見て、しきい値を適切に調整します。

## 安全な故障: アプリを動かしたまま監視だけを止める

**復旧はターミナル B で監視コマンドを再実行することです。**

1. ターミナル B で Ctrl+C を押し、監視だけを止める
2. アプリのターミナル A はそのままにする
3. 6 秒以上待つ

```bash
sleep 6
python3 watchdog.py --max-age 5
```

古い観測として失敗することを確認します。アプリが 200 を返せても、監視の観測が止まることはあります。

## 復旧

ターミナル B で繰り返し確認を再開します。

```bash
python3 monitor.py --path /items/1 --expect-name monitoring-demo --count 60 --interval 2
```

最初の CHECK が出てから、ターミナル C で再確認します。

```bash
python3 watchdog.py --max-age 5
```

最後の観測が新しくなったことを確かめます。

## 確かめた範囲: 同じホストでは、ホスト全体の停止を検知できない

**アプリ・監視・watchdog が同じ PC/Ubuntu にいると、PC 全体が止まったときに全部止まります。** 同じホストの別ターミナルで動かしただけでは、独立した監視地点にはなりません。さらに、この watchdog は1回実行して表示するだけなので、定期実行も外部への通知もまだありません。

実際のホスト停止を知るには、別ホストや外部サービスなど、同じ障害で一緒に止まらない場所から確認する設計が必要です。そのときは到達経路、認証、監視側の稼働、通知の到達性も考えます。本教材の実験用 HTTP サーバーをインターネットに公開する方法は取りません。

## チェックポイント

- アプリを止めても監視を動かし続けたら、watchdog は何を報告するか試す
- 「アプリは異常」「監視の観測は新しい」を同時に説明できるか
- PC の電源断を知るには、誰がどこから確認する必要があるか図にする
