# 整理と後片付け

## 手を動かした後で、名前を整理する

これまでに追加したものに、よく使われる名前を付けてみます。分類を覚えること自体がゴールではありません。

| 実際に確かめたこと | よく使われる呼び方 | 答えていた問い |
|---|---|---|
| URL が 200 を返す | HTTP 監視・外形監視 | この地点から返事を受け取れるか |
| 既知データを読み取れる | 操作監視・合成監視の小さな例 | 必要な処理が期待どおりに終わるか |
| 応答の所要時間 | レイテンシー監視 | 待ち時間は許容範囲か |
| ログと対象の状態を調べる | 内部の観測・原因調査 | どこで何が起きたか |
| 最終観測の鮮度 | 監視自身の監視 | 最近も確認が行われたか |

呼び方や分類はツールや組織によって重なります。アプリ・DB・OS・ネットワークという層の名前も、**次にどこを見るかを相談するための地図**として使えます。最初から全層の全項目を集める必要はありません。

メトリクスは数値の変化、ログは個々の出来事、トレースは処理のつながりを調べるときに役立ちます。この教材は数回の HTTP 確認とログの入口までで、時系列 DB や分散トレースは導入していません。

## 最後の演習: 一つの監視を設計する

自分が面倒を見る小さなサービスを1つ選び、次の 7 点を埋めます。まだ動かす必要はありません。

1. 利用者ができなくなると困る操作
2. 最初に1つだけ確かめることと、期待する結果
3. 確認地点、間隔、処理の待機上限
4. 異常と復旧を判断する条件
5. 誰へ、何を含めて知らせるか
6. 安全なテスト方法と、故障を戻す方法
7. 成功しても証明できないことと、監視自身が止まった場合の検知方法

「DB 接続に成功したからサービスは正常」のように、確認した範囲より大きな結論になっていないか、隣の人と確認してください。

## 次の一歩を決める

今の困りごとが「過去の傾向を見たい」なら、数値の保存とグラフ化を足します。「複数台の記録を並べたい」なら、時刻とラベルをそろえて集約します。「人が気づかない」なら、通知先と担当者、到達確認を足します。その段階で Prometheus、Grafana、マネージド監視サービスなどを比較すると、欲しい機能がはっきりします。

ツール名を先に選ぶより、いま答えられていない問いを1つ選びましょう。

## 後片付け

1. ターミナル B の監視を Ctrl+C で止める
2. ターミナル A のアプリを Ctrl+C で止める
3. 必要な観測記録や調査メモを保存する
4. 学習用状態だけを初期化する

```bash
python3 labctl.py reset
```

`.state/` の学習用 DB は初期状態になります。再開するときは同じフォルダーで `python3 app.py` を実行します。今後使わなければ、アプリと監視が停止したことを確認してから、作成した専用の `monitoring-workshop` フォルダーをエクスプローラーで削除して構いません。

共有フォルダーや別のプロジェクトを消さないように、削除先は画面で確認します。機械全体のコンテナー・DB・ログをまとめて消す操作は不要です。
