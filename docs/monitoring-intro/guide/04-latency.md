# 4. 成功していても、遅いと困る

## 困りごと

データは正しく返ります。でも毎回長く待つなら、利用者は困ります。次は「何が返ったか」に「何秒で返ったか」を足します。

## 小さな追加: 応答時間を条件にする

```bash
python3 monitor.py --path /items/1 --expect-name monitoring-demo --max-ms 500
```

ここでは確認を開始して、応答本文を受け取って子プロセスが終了するまでの時間が 500 ミリ秒を超えたら失敗とします。Python の子プロセスを起動・終了する時間も含むので、アプリの処理時間そのものとは異なります。500 ミリ秒は**実験用の値**であり、すべてのサービスに適した基準ではありません。まず正常時の値を数回見て、十分下回っているか確かめます。

## 安全な故障: この URL だけに待ち時間を入れる

**戻すコマンドは `python3 labctl.py delay 0` です。** CPU に負荷を掛けたり、ディスクを埋めたりしません。アプリの `/items/1` の処理に、最大 2 秒の待ち時間を入れるだけです。

```bash
python3 labctl.py delay 0.8
python3 monitor.py --path /items/1 --expect-name monitoring-demo --timeout 2
python3 monitor.py --path /items/1 --expect-name monitoring-demo --timeout 2 --max-ms 500
```

この比較では `--timeout 2` とし、0.8 秒の待ち時間に加えてプロセスの起動時間にも余裕を持たせます。前者は内容だけを見て成功し、後者は遅さを見て失敗します。HTTP 200 が返ったことと、体験として許容できる速さであることを分けて考えます。

次に、待ち時間を監視側の待機上限より長くします。

```bash
python3 labctl.py delay 2
python3 monitor.py --path /items/1 --expect-name monitoring-demo --max-ms 500
```

このコマンドでは `--timeout` を省略しているので、待機上限は既定の 1 秒に戻ります。今度は応答の完了を待てず、タイムアウトとして失敗することを確認します。

**応答時間のしきい値**は「受け取った応答を遅いと判定する値」、**タイムアウト**は「これ以上処理を待たないための上限」です。役割が違います。タイムアウトを延ばすだけでは、遅さそのものは直りません。

## 復旧

```bash
python3 labctl.py delay 0
python3 monitor.py --path /items/1 --expect-name monitoring-demo --max-ms 500
```

正常時の応答時間に戻り、同じ条件で成功することを確かめます。

## 確かめた範囲

今回の1回の読み取りが、この監視地点から見てどれくらいかかったかが分かりました。多数の利用者が同時にアクセスしたときの性能、全利用者の遅さ、パーセンタイルは分かりません。監視用リクエスト数回から、性能試験をしたとは言いません。

## チェックポイント

- タイムアウトと 500 ミリ秒のしきい値の違いを説明する
- 通常時・0.8 秒の遅延・2 秒の遅延を比較する
- 利用者が許容できる時間と、通常時のばらつきの両方を見て、しきい値を決める理由を考える
