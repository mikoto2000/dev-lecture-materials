# 6. 異常を見つけた後、必要な証拠から調べる

## 困りごと

「読み取りが失敗した」ことは分かりました。でも原因が DB、アプリ、通信のどれなのかは、監視結果だけでは決まりません。いきなり CPU・メモリー・ディスクの全グラフを並べず、今の失敗につながる証拠から調べます。

## 小さな追加: 同じ時刻のアプリログを見る

ターミナル A には、リクエストの UTC 時刻・パス・HTTP の状態・所要時間が記録されます。DB を開けなかった場合には、そのエラーも記録します。

次の順番で問いを狭めます。

1. 監視の CHECK は、いつ、どの URL で、どんな失敗だったか
2. 同じころのアプリログに、そのリクエストはあるか
3. リクエストがあるなら、どの処理まで進み、何が失敗したか
4. その仮説を確かめるために、1つだけ何を調べるか

## 安全な故障: 二つを一度に壊さない

**戻すコマンドは `python3 labctl.py db-unavailable off` です。**

```bash
python3 labctl.py db-unavailable on
python3 monitor.py --path /items/1 --expect-name monitoring-demo
python3 labctl.py inspect
```

監視では 503、アプリログでは DB を開く処理の失敗、`inspect` では学習用 DB の場所と状態を確認します。`inspect` はこの教材のファイルと既知データを読む補助コマンドです。OS 全体や本番の情報を収集しません。

「503 だから必ず DB の問題」と決めつけないでください。今回はログと DB ファイルの状態を合わせて、その説明を支持する証拠が得られました。

## 復旧と再確認

```bash
python3 labctl.py db-unavailable off
python3 monitor.py --path /items/1 --expect-name monitoring-demo
python3 labctl.py inspect
```

監視が成功し、アプリログでも正常な応答が確認できることを確かめます。

次に前章までの故障を1つずつ選び、同じ順番で調べます。

- アプリ停止: 接続失敗。停止中のリクエストはアプリログに到達しない
- 名前の変更: 200 だが内容不一致。学習用の既知データを確認する
- 待ち時間: 応答が遅い。アプリ側の所要時間と、設定した待ち時間を比べる

ログがないことだけでネットワーク障害と断定はできません。別の場所を見ている、ログが遅れている、ログ記録自体が壊れている可能性もあります。

## 確かめた範囲

監視結果と同じ時刻のログ、学習用 DB の状態を結び付けて、今回の故障の原因を絞れました。ほかのサービスや機械の状態まで分かったわけではありません。

## ここで初めて、追加の観測先を考える

| 手がかり | 次に確認したいこと | 確認できても残る限界 |
|---|---|---|
| DB 接続エラーが出る | 対象 DB への接続・認証・稼働状態 | 接続成功だけで業務クエリーの正しさは分からない |
| DB 処理の時間が長い | 該当クエリーの時間・ロック待ち | DB 以外の待ち時間は別に調べる |
| アプリの処理が全体に遅い | その時刻の対象プロセスの CPU・メモリー | 値が高いだけで原因とは断定できない |
| 保存に失敗している | 対象の保存先の空き容量・権限 | 空きがあるだけで書き込み成功とは限らない |

この表は次の調査の候補です。本教材で実 DB サーバーや OS 資源監視を実装したわけではありません。ディスクを満杯にする、機械全体に負荷を掛ける、共有プロセスを止める実験は行いません。
