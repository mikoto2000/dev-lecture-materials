Kuma 移行時の [PR #6 の CI](https://github.com/mikoto2000/dev-lecture-materials/actions/runs/37794254728) では、実イメージの起動、通信、状態保持、通知受信、後片付けがすべて成功しました。

Kuma 本体の試験では、通常の初期化と使い捨てのローカル実験アカウントを使用しました。独立した一時フォルダーで実行し、実際の利用者アカウントや外部通知先は使っていません。

- HTTP の正常・停止・復旧
- HTTP 200 の誤データを Keyword と Json Query で検知
- SQLite ファイルの退避では health が Up、item が 503 / Down
- 1.5 秒の待ち時間は timeout 3 秒で Up、1 秒で Down
- Retries 2 では2回 Pending の後、3回目の連続失敗で Down
- Pending からの回復では通知なし
- Webhook Test、Down、Up をローカル受信器で確認
- Resend 0 では継続 Down の追加2回で通知が増えず、復旧時は Up が1件

応答時間の実測は 1504 ms でした。これは試験時の値であり、受講者の環境で同じ値になるとは限りません。教材の複合 JSONata 式も、公式の評価関数で正常値・誤った名前・誤った ID を確認しました。

Compose の CI は、固定版イメージの起動、サービス名による通信、実際の故障、再起動後の状態保持、独立した通知受信器、down 後のボリューム保持、専用プロジェクトの後片付けを試験します。この試験だけで GUI の監視設定を操作したとは扱いません。対象 PR の compose ジョブが成功したコミットを公開対象とします。

## 学習順と資源観測の追加

利用者の操作 → 通知 → 遅さ → ログ → 容量 → CPU・メモリー → 通信の順へ調整しました。新しい実 Docker 試験は次のコマンドを対象にします。

- demo の `/lab/.state` に対する `df -h` と `df -i`
- demo と kuma を個別に指定した `docker compose stats --no-stream`
- Kuma から demo を調べる `getent hosts`
- 回数3・応答待ち1秒・全体期限5秒を指定した `ping`
- アプリが誤ったデータを返していても、同じ宛先へ ICMP が届くこと

コマンドは試験用プロジェクトの対象だけに限定し、外側の実行にも時間上限を設けます。CPU・メモリーの固定パーセントや空き容量を、環境共通の成功条件にはしません。1回の観察で分かるのは、その時点の対象の値です。継続監視の構築や Windows ホスト全体の検証は対象外です。

コマンド単体試験では出力を差し替え、対象・引数・上限・結果の読み取りを検査します。その成功と、実際の Docker イメージ内での実行成功を区別します。後者は対象 PR の compose ジョブで確認します。
