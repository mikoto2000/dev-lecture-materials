# 困ったとき

## Python が見つからない・Windows の Python が動く

今のターミナルが Ubuntu の Bash か確認します。`python3 --version` と `pwd` を実行してください。PowerShell のままなら、[準備](./guide/00-prepare.md)の WSL に入る手順へ戻ります。

## ファイルが見つからない

`pwd` と `ls` で、`app.py` などがあるフォルダーを確認します。2つ以上の ZIP 展開先を混ぜず、すべてのターミナルから同じファイルを使います。状態はスクリプトと同じ場所の `.state/` に置かれます。

## Address already in use と表示される

同じ実験アプリを既に別のターミナルで起動していないか確認します。自分で起動したアプリなら、そのターミナルへ戻って Ctrl+C を押します。別のサービスが 18080 番を使っている場合は、勝手に停止しないで講師へ相談します。本教材のスクリプトは接続先を固定しているので、片方だけポート番号を変えないでください。

## `/health` は成功するが `/items/1` は失敗する

第 3 章の DB 故障、第 4 章の待ち時間が残っていないか確認します。

```bash
python3 labctl.py inspect
python3 labctl.py db-unavailable off
python3 labctl.py wrong-data off
python3 labctl.py delay 0
```

それでも戻らなければ、アプリと監視を Ctrl+C で止め、記録を保存してから `python3 labctl.py reset` で学習用状態だけを初期化します。

## 500 ミリ秒を正常時にも超える

まず待ち時間を 0 にし、数回計測します。PC の起動直後や別の処理の影響もあり得ます。教材の 500 ミリ秒は普遍的な基準ではありません。講師と相談し、正常時と実験用の待ち時間を区別できる条件に調整します。機械全体に負荷を掛ける操作はしません。

## ALERT が一度しか出ない・RECOVERY がすぐ出ない

第 5 章の仕様です。CHECK は毎回出し、ALERT は連続失敗が条件を満たしたとき、RECOVERY はその後の連続成功が条件を満たしたときに出します。監視を再起動すると通知状態は引き継がれません。

## watchdog が古い観測と報告する

監視が回数上限で終了していないか確認します。監視を再実行し、最初の CHECK が出てから試します。監視と watchdog は、同じ ZIP の展開先を使います。最終観測は UTC の時計で比較するため、PC の時刻が大きく変わった場合にも注意してください。

## コマンドが失敗の終了コードで終わる

故障を検知する実験では正常です。`monitor.py` と `watchdog.py` は、条件を満たさないときに成功以外の終了コードを返します。エラーを消すだけでなく、何を検知したのか読み取ってください。
