# 5. 調査と後片付け

## この章のゴール

観測した事実と原因の候補を分け、次に何を見るかを決めます。

## 通知から調査へ

第2章で読み込んだ `$logs` から、異常窓のリクエストを探します。変数がなければ、第2章の読み込みをやり直してください。

```powershell
$logs | Where-Object { $_.request_id -eq 'req-013' } | Format-List
```

このリクエストは `/items` に対する503で、1800 ms かかっています。**DB の故障と断定できる情報はありません。** 同じ ID のアプリログ、プロキシのエラーログ、依存先の状態を調べる段階です。この教材には、それらの追加ログは含まれていません。

| 観測した事実 | 次に確認すること |
|---|---|
| 5xx が増えた | アプリ例外、プロキシの接続エラー、デプロイ時刻 |
| 200のまま遅くなった | DB の処理時間、外部 API、待ち行列、資源の履歴 |
| 404が増えた | パスの分布、リンク変更、ルーティング設定 |
| ログが来ない | 外形監視、収集器の稼働、転送遅延、保存先の容量 |

同時刻に CPU が高くても、それだけで原因と確定できません。時刻をそろえ、正常時との違いと変更履歴を照合します。[インフラ監視実践入門](../../monitoring-intro/index.md)では、外形監視と内部の観測を組み合わせて学べます。

## ログを安全に扱う

実際のログには、IP アドレス、ユーザー ID、検索語などが含まれることがあります。URL のクエリー、Cookie、Authorization ヘッダー、パスワード、トークンは不用意に記録しません。パス自体に個人情報が含まれる設計にも注意します。

共有する前に必要な項目だけに絞り、マスクします。保存期間、閲覧できる人、削除手順も決めます。リクエスト ID も他の情報と結び付けられるため、公開してよいとは限りません。

## 振り返り

次の問いに、自分の言葉で答えてください。

1. 5xx が3件という情報だけで、影響の大きさを判断するために足りないもの
2. HTTP 200でも遅いリクエストを見つけるための項目
3. ログが0件の時間窓を正常と扱えない理由
4. `ALERT` の次が `LOW_TRAFFIC` だった場合の、復旧通知の扱い
5. アクセスログで503を見つけた後に調べる情報

答えの例は[講師用ガイド](../facilitator.md)にあります。

## 後片付け

起動したサーバーや作成した外部アカウントはありません。PowerShell を閉じれば変数も消えます。配布した2ファイルと自分のメモが不要なら、保存した `access-log-lab` フォルダーだけをエクスプローラーで削除してください。
