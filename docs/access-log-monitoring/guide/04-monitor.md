# 4. 監視の条件を決める

## この章のゴール

判定を繰り返すときの条件と、通知を受けた後の行動を決めます。

## まずは単純な条件

付属スクリプトは次の順番で、時間窓ごとに状態を返します。

| 条件 | State | 読み方 |
|---|---|---|
| リクエストが0件 | NO_DATA | 正常かどうか判断できない |
| 1〜9件 | LOW_TRAFFIC | 判定に必要な母数に足りない |
| 10件以上で、5xx 率が20%以上、または遅いリクエストが3件以上 | ALERT | 調査が必要 |
| 10件以上で上の条件に当たらない | OK | この条件では異常を検出していない |

閾値は演習用です。業務の重要度、通常のアクセス数、許容する失敗や遅延を確認して決めます。母数の条件を置くと少数の失敗を通知しなくなるため、低頻度でも失敗を見逃せない操作には別の条件が必要です。

## データがない時間を試す

```powershell
.\Measure-AccessLog.ps1 -Path .\access.jsonl -End '2026-11-18T00:04:00Z'
```

`Requests` は `0`、`State` は `NO_DATA` です。エラー率と p95 は空欄になります。アクセスがない場合のほか、サービスに到達できない可能性もあります。収集の停止や保存先の指定ミスも調べます。**0件を「エラー率0%で正常」と扱ってはいけません。**

```powershell
.\Measure-AccessLog.ps1 -Path .\access.jsonl -End '2026-11-18T00:00:15Z'
```

これは3件だけを含む時間窓となり、`LOW_TRAFFIC` です。どちらも `OK` への復旧とは区別します。

## 通知の条件を紙に書く

スクリプトは1回分を集計するだけで、以前の状態を保存したり通知したりしません。次のルールで運用するなら、状態を保存する仕組みを別に用意します。

1. 毎分、直前の確定した1分間を集計する
2. 初めて `ALERT` になったら、対象・時間窓・件数・率・調査先を通知する
3. `ALERT` が続いても毎分同じ通知を送らず、必要な再通知間隔を決める
4. `ALERT` の後で十分な母数の `OK` が2窓続いたら、復旧を1回通知する
5. `NO_DATA`、`LOW_TRAFFIC`、読み取り失敗では復旧とせず、データの状態を別に調べる

本教材の復旧データは1窓分です。このルールなら「復旧候補」まで確認でき、復旧通知にはもう1窓必要です。最初から2窓の連続異常を要求すると通知は遅れるため、短い障害への対応時間との釣り合いも考えます。

## 継続監視へ進むには

定期実行では `-End` に現在時刻を使えます。時刻を分境界へそろえ、収集遅延を待つ設計も必要です。固定した過去の `-End` のまま起動すると、同じ窓を何度も評価してしまいます。

実環境では、Vector や Fluent Bit などで収集し、Loki や OpenSearch などで検索・集計する構成も選べます。導入前に次を確認します。

- 収集の遅延、欠損、重複、時刻のずれをどう検出するか
- ログのローテーション時に、最後の位置や新しいファイルをどう追うか
- 間に合わなかったログを再集計するか、通知の重複をどう防ぐか
- ログの入口ごとに形式や単位が違っても、同じ意味へそろえられるか
- 収集器自身の停止と保存先の容量を、どこから監視するか

サンプル全体を毎回読み直す付属スクリプトは、大規模ログの収集器には適しません。外部からの HTTP 監視も併用します。これで、リクエストが入口まで届かずアクセスログが残らない障害も調べられます。
