# アクセスログ分析入門 - 不正アクセス検知編

アクセスログから「いつ、どこから、何にアクセスしたか」を調べ、不正利用を疑う根拠を説明する教材です。正常時のログと比較し、誤検知の可能性を確かめ、追加で必要な情報を整理します。

ブラウザーの基本操作ができる方を対象とした、90〜120分のハンズオンです。HTTPやログ分析の経験は問いません。Docker、Grafana、プログラミング言語の導入は不要です。

## できるようになること

- 時刻、送信元IP、パス、HTTPステータスを読む
- 時間帯・送信元・アクセス先ごとに件数と分布を比較する
- 探索的なアクセスや認証失敗の集中を見つける
- 観測した事実と仮説を分け、判断を保留する理由も説明する

## 1. アクセスログの1行を読む

Webブラウザーなどがサーバーへ送る要求をHTTPリクエストと呼びます。アクセスログは、その要求に対してサーバーが記録した情報です。この教材は、1行が1つのJSONオブジェクトとなるJSONL形式を使います。

```json
{"time":"2026-11-01T09:00:00Z","client_ip":"192.0.2.1","method":"GET","path":"/","status":200,"user_agent":"LearningBrowser/1.0","request_id":"req-0001","event":"access"}
```

| 項目 | 意味と読み方 |
|---|---|
| `time` | 発生時刻。末尾の `Z` はUTCを表す。09:00 UTCは日本時間18:00 |
| `client_ip` | 記録側から見た送信元IP。利用者本人を識別する値ではない |
| `method` | `GET` は取得、`POST` はデータ送信などに使う |
| `path` | 要求先。教材では `?` 以降の検索条件も含めた値 |
| `status` | HTTPの応答結果。200は成功、401は認証要求・認証情報の問題、403は拒否、404は対象が見つからないことを示す |
| `user_agent` | クライアントの自己申告。変更できるため本人確認には使えない |
| `request_id` | 要求を別のログと照合するための識別子 |
| `event` | `access` は通常のアクセス記録、`auth` は認証結果を付加した記録 |
| `account` / `outcome` | 認証対象と結果。認証イベントだけが持ち、結果は `success` または `failure` |

認証イベントは、同じ要求をアクセスログと認証ログに重複記録したものではありません。教材では1要求を1行で記録します。実際のサービスでは別々のログを照合することがあります。

HTTPの4xxはクライアント側の要求に関連するエラー、5xxはサーバー側のエラーです。401だけで「パスワードを間違えた」と判断できません。認証の成否は、アプリが記録した `event` と `outcome` を確認します。200も、侵入成功や安全性の証明にはなりません。

送信元は文書用IPアドレス、アカウントは架空の識別子です。記録時刻は2026年11月1日の09:00以上09:10未満（UTC）です。外部サイトへのアクセスは必要ありません。

### ツールの使い方

1. サンプルを選び、「サンプルを読み込む」を押す。初期表示は「01 正常時」。
2. 集計単位を選び、「集計する」を押す。最初は「1分ごと」。
3. 時刻・IP・パスなどを指定して、もう一度集計する。条件はすべてANDで結合する。
4. 別の観点を調べる前に、「条件をリセット」を押す。ログはそのまま、条件と集計単位が戻る。

時間はすべてUTCとして入力します。09:03の1分間は、開始 `2026-11-01T09:03:00`、終了 `2026-11-01T09:04:00` です。終了時刻の行は含めません。IPとステータスは完全一致、パスは大文字・小文字を区別した部分一致です。

集計は条件に合う全ログが対象です。パス種類数はクエリー文字列を含む値の種類数であり、ページの数と一致するとは限りません。集計結果と明細はそれぞれ最大500行だけ表示します。表示が省略された場合は条件を絞ってください。入力上限はUTF-8の2 MiB・10,000行です。不正な行は行番号を表示して除外します。除外があれば分析対象が欠けていることを記録します。

## 2. 正常時の分布を知る

「01 正常時」を読み込み、次を調べます。このサンプルは通常時という背景情報が与えられています。実務では、曜日・営業時間・変更履歴などを含めて比較対象を選びます。

1. 「1分ごと」で集計し、総件数、1分あたりの件数、エラーの割合を記録する。
2. 「送信元IP」で集計し、IPの数とそれぞれの件数を記録する。
3. 「パス」で集計し、よく使われる要求先を確認する。

期待する結果は60件、毎分6件、4xx・5xxは0件です。送信元は3つで各20件、パスは `/`、`/help`、`/products` が各20件です。各IPは1つのパスにだけアクセスします。学習用に単純化した値であり、「毎分6件より多ければ異常」という基準ではありません。

固定した1分区間での件数と、監視で使う任意の時点からの「直近1分」は異なります。このツールの「1分ごと」は、秒が00から次の分の00未満までの固定区間です。ログのない分は0の行を表示しません。

## 3. ガイド演習：404の増加を調べる

「02 ガイド演習」を読み込みます。正常時の60件に、追加のアクセスが混ざっています。まず解答を見ずに操作してください。

### 例題：増加した時間を見つける

「1分ごと」で集計すると、09:03は36件、09:06は30件です。他の分は6件です。正常時と比べて何が増えたのか、ステータスと送信元で絞ります。

### 演習A：09:03のアクセス

1. 開始09:03、終了09:04に設定し、HTTPステータスに `404` を入力する。
2. 「送信元IP」で集計し、IPと件数を記録する。
3. 集計単位を「パス」に変え、分布を確認する。
4. 「ログ明細」の時刻とメソッドを確認する。

問い：どんな行動が疑われますか。404が返ったことで、何が分かり、何が未確認でしょうか。

ヒント：管理機能や設定ファイルを探しているようなパスに注目します。外部サイトでそのパスを試す必要はありません。

### 演習B：09:06との比較

条件をリセットして、開始09:06、終了09:07、ステータス `404` を指定します。送信元とパスをそれぞれ集計してください。

講師からの追加情報：09:06にはヘルプページへのリンク変更があり、古いURLへの案内が残っていました。

問い：件数以外に、演習Aと判断を分ける情報は何ですか。リンク変更の情報がなければ、何を追加確認しますか。

## 4. 総合演習：調査メモを作る

「03 総合演習」を読み込みます。ガイド演習とは別のログです。正常時の60件に複数の動きが加わっています。目安は25分です。

架空の運用担当者から、次の情報が届きました。

- 09:02には記事一覧を巡回する正規クローラーを実行する予定だった。実行記録との照合はまだ済んでいない。
- `192.0.2.200` は共有ネットワークの出口として使っている。
- 認証結果はアプリが判定したものだが、利用者への確認はまだ行っていない。

### 調べること

1. 全体の件数と、件数が多い送信元を確認する。最も多い送信元を攻撃者と断定できるか。
2. `event=auth`、`outcome=failure` で絞り、送信元別・アカウント別に集計する。
3. `learner-a` に何が起きたか、`/login` の成功・失敗の時系列を明細で確認する。アカウントは明細と集計で照合する。
4. 少数ずつ失敗している送信元について、同じアカウントを対象にしているか確認する。
5. `203.0.113.60` のアクセス先を読み、疑う理由とログだけでは分からないことを整理する。

ヒント：IP別の件数だけでなく、認証対象の共通性、成功への変化、検索条件の文字列も調べます。ツールはパーセントエンコードを自動で復号しません。`%27` は単一引用符、`%20` は空白、`%3D` は `=`、`%2F` は `/`、`%3C` と `%3E` は山括弧です。

### 提出する調査メモ

最低2つの調査対象について、次の表を埋めてください。件数と要求IDは、自分の画面で確認した値を記録します。根拠となる行を引用し、仮説は断定と区別します。

| 項目 | 記入する内容 |
|---|---|
| 調査範囲 | サンプル名、開始・終了時刻、UTC、使用した条件、除外行の有無 |
| 事実 | 送信元、対象、件数、結果、時系列、要求ID |
| 仮説 | 認証の試行、正規クローラー、共有IPなどの候補 |
| 未確認事項 | 本人の操作か、処理が成功したか、影響が出たか |
| 追加調査 | 認証・アプリ・プロキシ・WAFのログ、変更履歴など |
| 次の行動 | 確認の担当者、優先度、その理由 |

観測が欠けている可能性も考えます。アクセスログにない操作や、記録されなかった要求までは確認できません。

## 5. 解説と振り返り

ここから先は解答です。演習を終えてから確認してください。

### ガイド演習の解説

| 対象 | 観測できる事実 | 判断と追加調査 |
|---|---|---|
| 09:03 | `203.0.113.10` から30件、すべて404。`/admin`、`/backup.zip`、`/.env` が各10件 | 管理画面や機密ファイルの探索を疑う。404はその要求で見つからなかったことを示すが、他の要求での取得成功や侵入の有無は不明 |
| 09:06 | `198.51.100.20` から `/old-help` へ24件、すべて404 | 与えられた変更情報と合わせ、リンク切れを第一候補にする。リンク元と変更履歴を確認する |

全体は114件、404は54件で約47.4%です。この割合だけでは攻撃とリンク切れを区別できません。単一パスなら安全、複数パスなら攻撃、という基準にもなりません。

### 総合演習の照合表

全体は154件です。HTTPエラーは31件（約20.1%）、アプリが記録した認証失敗は30件です。403の1件は認証失敗として数えません。

| 対象 | 件数と観測 | 解釈・追加確認 |
|---|---|---|
| `198.51.100.30` | 09:02に40件、記事10種類、すべて200 | 最多だが予定された巡回と整合する。User-Agentだけを信用せず、実行元やジョブ履歴と照合する |
| `203.0.113.40` | 09:04に `learner-a` の失敗12件、その後09:04:52に成功1件 | 認証試行の集中を疑い、成功が正当か優先して確認する。本人の入力ミスの可能性もある。成功を理由に調査を終えない |
| `203.0.113.70` 〜 `203.0.113.75` | 09:05に各3件、合計18件、すべて `learner-b` の認証失敗 | 分散した試行を疑う。各IPだけで集計すると目立たない。アカウント別の履歴や他時間帯も確認する |
| `192.0.2.200` | 09:07に20件、2種類のUser-Agent、すべて200 | 共有IPという情報と整合するが、利用者数は確定できない。IPやUser-Agentを人数として数えない |
| `203.0.113.60` | 09:08に3件。検索条件にSQL風の式、親ディレクトリーへの参照、スクリプト風の文字列。応答は200・403・200 | SQLインジェクション、パストラバーサル、XSSを狙った入力を疑う。実行・情報取得・ブラウザーでの実行が成功したかは別途確認する |

`/search?q=%27%20OR%201%3D1--` を復号すると、検索値に `' OR 1=1--` が含まれます。`../` は親ディレクトリーへの参照、`<script>` はHTMLのスクリプト要素です。見慣れない入力を観測した事実と、脆弱性が悪用されたという結論は別です。200は検索画面やエラー説明のページを返した結果である可能性もあります。

実際のサービスでは、クエリー文字列に個人情報や秘密を含む場合があります。この教材は架空の固定文字列だけを記録しています。本番で同じ記録方針をそのまま採用せず、必要な項目の選別・マスキング・閲覧権限・保存期間を決めます。

### 調査メモの記入例

事実：総合演習の09:04:00以上09:05:00未満（UTC）に、`203.0.113.40` から `learner-a` への認証失敗12件、その後の成功1件を観測した。認証要求のIDは `req-0115` 〜 `req-0127`。有効13件、除外なし。

仮説：第三者による認証試行か、本人の入力ミスの可能性がある。ログだけでは成功の正当性は分からない。

次の行動：認証担当者へ確認を依頼し、本人への照会と、成功後のセッション・操作履歴を優先して調べる。IPだけで一律に遮断する判断は、共有利用の影響も確認して行う。

### 振り返り

- 同じ404増加でも、追加調査が変わったのはなぜか。
- 件数が最多の送信元を優先するだけでは、何を見逃すか。
- HTTPステータスと認証結果を分ける理由は何か。
- 200や認証成功を見たとき、何を追加で確認するか。
- 自分の調査メモで、事実と仮説が混ざっていないか。

継続して検知する仕組みを学ぶ場合は、[アクセスログ監視入門](../access-log-monitoring/index.md)、[不正アクセス監視入門](../security-log-monitoring/index.md)へ進みます。この教材は保存済みログの分析を扱い、常時監視や自動遮断は設定しません。

## 困ったとき

### ツールが動かない

ZIPを展開し、`analyzer.html` と同じフォルダーに `core.js`、`app.js`、`samples.js`、`style.css` があることを確認します。JavaScriptを有効にした最新のEdge、Chrome、Firefoxを使います。組織の設定でローカルファイルのスクリプトが制限されている場合は、公開サイトのツールを使ってください。

### 期待した件数にならない

選択中のサンプルを確認し、「条件をリセット」してから入力し直します。時間はUTC、終了は含みません。サンプル切り替え後は「サンプルを読み込む」を押します。行の形式エラーや表示上限も確認します。認証結果の条件を指定すると、結果を持たない通常アクセスは除外されます。

## 講師用ガイド

開催前にオンライン版とZIP展開版を受講者のブラウザーで開き、正常時60件、ガイド演習114件、総合演習154件を確認してください。各自の画面はUTCで統一します。解説を先に見ないよう、総合演習の終了を区切ってから答え合わせします。

評価は、正解のIPを挙げたかだけで決めません。時間範囲・件数・要求IDを示せたか、仮説を複数挙げたか、追加調査が仮説に対応しているかを確認します。正常時のログも単純化されており、実際の負荷や季節変動を再現していないと補足します。

ツールは任意のWebサーバーの生ログを自動で取り込むものではありません。読み込めるのは本教材の項目を持つJSONLです。認証以外は表の8項目が必須です。認証には `account` と `outcome` も必要です。対応する時刻はUTCの `YYYY-MM-DDTHH:mm:ssZ` またはミリ秒3桁付きです。出所や重複の正当性、IPの形式は検証しません。

開発者は `npm run package:log-analysis` でサンプル・内蔵データ・オフライン本文・ZIPを再生成します。`npm run test:log-analysis` で分析結果、境界時刻、形式エラー、配布物の整合性を確認します。再生成にはPython 3が必要です。受講者には不要です。
