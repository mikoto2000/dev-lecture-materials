- 実際の Kuma に画面と同じ設定を API で登録し、HTTP・キーワード・JSON Query の判定を確認
- 2秒の遅延に対し、タイムアウト1秒で Down、3秒で Up になることを確認
- 再試行2回の設定で Pending → Pending → Down を確認。Test・Down・Up の Webhook を受信器で確認
- アプリ停止・再開、SQLite ファイルの退避と復旧、誤データ、遅延、停止中のリセットを確認
- `df`、`docker compose stats`、Kuma からの `getent` と `ping` を実行
- `down` 後もデータが残ることと、`down --volumes` で検証用ボリュームが削除されることを確認
- WSL 上で Python ラボと資源コマンドの試験25件に成功

| 新しい Down の3回目 | 赤い棒3本 | 01:41:15 | 16:41:15.289（最初の再通知） |
| 新しい Down の4回目 | 赤い棒4本 | 01:41:35 | 追加受信なし |
| 新しい Down の5回目 | 赤い棒5本 | 01:41:55 | 16:41:55.292（2回目の再通知） |

画面のイベント表には初回の Down が01:40:34の行として残りました。赤い棒の4本目では受信件数が増えず、5本目のチェックと同じ秒に2回目の再通知が1件届きました。最初の再通知から約40秒後でした。

## 通知の追加実験

通知の基本操作を終えたあと、復旧のタイミングや Kuma の再起動を変えて試せます。各ケースの観測時刻と受信件数は、上の検証結果に記録しています。

### Pending のうちに復旧する場合

`Retries` は **2** のままにします。`demo-health` が Up であることを確認し、受信ログの `demo-health` の Down 通知と Up 通知の件数を控えます。

1. `docker compose stop demo` を実行する
2. 詳細画面上部の右端に新しいオレンジの棒が2本増えたら、すぐに `docker compose start demo` を実行する
3. 次のチェックでオレンジの棒に続いて緑の棒が加わり、状態が **Up** に戻ることを確認する
4. 受信ログを開き、`demo-health` の Down 通知と Up 通知の件数を停止前と比べる

Down が確定する前に応答が戻ると、どちらの通知も増えません。画面下のイベント表にも新しい Up の行は出ないため、画面上部の緑の棒と Up の表示で復旧を確認します。

### 復旧後にもう一度停止する

**Retries** と **Resend Notification if Down X times consecutively** を **2** のままにします。

1. Up の状態で `docker compose stop demo` を実行する。初回の Down 通知を確認する。新しい赤い棒が2本になったら、すぐに `docker compose start demo` を実行する
2. 画面で Up に戻り、復旧通知が1件届くまで待つ。最初の停止に対する Down 通知が1件のままであることを受信ログで確認する
3. 同じ設定で、もう一度 `docker compose stop demo` を実行する。復旧を示す緑の棒より後の、新しい赤い棒だけを数える
4. 新しい赤い棒の1本目で初回の Down 通知を確認する。2本目では受信件数が増えず、3本目で再通知が1件届くことを確かめる
5. `docker compose start demo` を実行し、Up への復旧を確認する

### Down の途中で Kuma だけを再起動する

**Retries** と **Resend Notification if Down X times consecutively** を **2** に設定したまま、Up の状態から始めます。

別の PowerShell で受信ログを表示しておきます。

```powershell
docker compose --profile notifications logs --follow --tail 20 notification-sink
```

1. `docker compose stop demo` でアプリを止める。下の表で試したいタイミングになったら、すぐに `docker compose restart kuma` を実行する
2. `docker compose --profile notifications ps --all` で、`demo` は停止中、`notification-sink` は稼働中と確認する
3. Kuma の画面が再接続したら `demo-health` の詳細を開く。再起動後に増えた赤い棒の時刻を受信ログと照合する
4. `docker compose start demo` を実行する。最初のチェックがまだ Down なら、次のチェックを待つ。Up の表示と復旧通知を確認する

Kuma 2.5.5 では、再起動後も Down が続き、再通知のカウントが引き継がれます。

| 再起動のタイミング | 再起動後の1回目 | 再起動後に再通知が届くチェック |
|---|---|---|
| 初回の Down 通知の直後（赤い棒1本） | 赤い棒が2本になる。初回通知は重複しない | 2回目（赤い棒3本） |
| 初回通知から1回チェックが進んだ直後（赤い棒2本） | 赤い棒が3本になり、再通知が届く | 1回目（赤い棒3本） |
| 最初の再通知の直後（赤い棒3本） | 赤い棒が4本になる。再通知は重複しない | 2回目（赤い棒5本） |
| 最初の再通知から1回チェックが進んだ直後（赤い棒4本） | 赤い棒が5本になり、次の再通知が届く | 1回目（赤い棒5本） |

棒は今回の停止で増えた分を数えます。初回通知と再通知は、どちらも受信ログでは `heartbeat_status` が `0` です。

### Kuma を停止している間にアプリを復旧する

**Retries** と **Resend Notification if Down X times consecutively** を **2** のままにします。Up の状態から始め、別の PowerShell で受信ログを表示しておきます。

1. `docker compose stop demo` でアプリを止める。最初の再通知を受信し、新しい赤い棒が4本になったら、すぐに `docker compose stop kuma` を実行する
2. Kuma の停止が完了したら、`docker compose start demo` でアプリを再開する
3. `(Invoke-WebRequest http://127.0.0.1:18080/health).StatusCode` が `200` を返すことを確かめる。起動直後に接続できなければ、少し待って再確認する
4. `docker compose start kuma` を実行する。画面が再接続したら、赤い棒4本に続いて緑の棒が1本増え、Up に戻ることを確認する
5. 画面の Up イベント時刻と Webhook の受信時刻を照合する。さらに2回分のチェックを待ち、Down の再通知が増えず、Up 通知が1件だけ届いたことを確かめる

#### 復旧後にもう一度アプリを止める

Up と復旧通知を確認したあと、同じ設定で `docker compose stop demo` を実行します。復旧を示す緑の棒より後だけを数えます。

オレンジの棒が2本続き、新しい赤い棒の1本目で初回の Down 通知が届きます。2本目で受信件数が増えず、3本目で最初の再通知が届くことを受信ログで確かめます。最後に `docker compose start demo` を実行し、Up に戻るまで待ちます。

#### Kuma の停止中にアプリを再停止する

同じ設定で Up から始めます。最初の再通知の次のチェックで赤い棒が4本になったら、上の手順と同じように Kuma を停止し、アプリを再開します。

1. アプリの `/health` が HTTP 200 を返すことを確認する
2. Kuma を停止したまま `docker compose stop demo` を実行する。アプリの停止が完了してから `docker compose start kuma` を実行する
3. 再接続後の画面で、赤い棒4本に続いて5本目が加わり、Down が続くことを確認する
4. 受信ログを照合する。Up 通知は届かず、Kuma 起動後の最初のチェックで再通知が1件届く
5. `docker compose start demo` を実行し、画面が Up に戻るまで待つ

Kuma 2.5.5 では、停止中にアプリが応答していた間のチェックはありません。Kuma が最後に記録した状態は Down のため、再通知のカウントが引き継がれます。

### Pending の途中で Kuma だけを再起動する

**Retries** と **Resend Notification if Down X times consecutively** を **2** のままにします。通常の確認間隔と再試行間隔を20秒にし、Up の状態から始めます。

1. `docker compose stop demo` を実行する。試したい回の **Pending** が出た直後に `docker compose restart kuma` を実行する。1回目なら新しいオレンジの棒が1本、2回目なら2本が目印
2. `docker compose --profile notifications ps --all` で、`demo` は停止中、`notification-sink` は稼働中と確認する
3. 画面が再接続したら、`demo-health` の詳細で再起動後に増えた棒を確認する
4. 赤い棒が加わり **Down** になったら、画面のイベント時刻と Webhook の初回 Down 通知の受信時刻を照合する
5. `docker compose start demo` を実行し、画面が Up に戻るまで待つ

Kuma 2.5.5 では、再試行のカウントが引き継がれます。

| 再起動のタイミング | 再起動後の1回目 | Down の確定と初回通知 |
|---|---|---|
| 1回目の Pending の直後 | オレンジの棒がもう1本増え、Pending が続く。通知はまだ届かない | 2回目のチェック |
| 2回目の Pending の直後 | 赤い棒が加わり、Down になる | 最初のチェック |

再接続した時点でチェックが進んでいる場合は、`docker compose logs --tail 50 kuma` で `Retry: 1`、`Retry: 2` とシャットダウンの行の順番を確認できます。

#### Pending で Kuma を止め、停止中にアプリを再停止する

同じ設定で Up から始めます。

1. `docker compose stop demo` でアプリを止める。試したい回の Pending が出たら、すぐに `docker compose stop kuma` を実行する。オレンジの棒は1回目で1本、2回目で2本になる
2. Kuma の停止が完了したら、`docker compose start demo` でアプリを再開する。前の手順と同じように `/health` の HTTP 200 を確認する
3. Kuma を停止したまま `docker compose stop demo` を実行する。アプリの停止が完了してから `docker compose start kuma` を実行する
4. 再接続した画面で、上の表と同じ回数のチェックで Down になることを確認する。1回目の Pending で止めた場合は起動後の2回目、2回目で止めた場合は起動後の最初のチェック
5. 画面の Down イベント時刻と初回通知の受信時刻を照合する。アプリを最後に再開するまで、Up 通知が届いていないことも確かめる
6. `docker compose start demo` を実行し、画面が Up に戻るまで待つ

Kuma 2.5.5 では、停止中のアプリの応答はチェックされず、停止前の再試行カウントが引き継がれます。

#### Pending で Kuma を止め、停止中にアプリを復旧する

同じ設定で Up から始めます。停止前に `demo-health` の Down 通知と Up 通知の件数を控えます。

1. `docker compose stop demo` でアプリを止める。試したい回の Pending が出たら、すぐに `docker compose stop kuma` を実行する。オレンジの棒は1回目で1本、2回目で2本になる
2. Kuma の停止が完了したら、`docker compose start demo` でアプリを再開する。`/health` が HTTP 200 を返すことを確認する
3. アプリを稼働させたまま `docker compose start kuma` を実行する。起動後の最初のチェックで、オレンジの棒のあとに緑の棒が加わり、Up に戻ることを確認する
4. 受信ログで Down 通知と Up 通知の件数が増えていないことを確かめる

Down が確定する前に応答が戻ったため、イベント表には新しい Up の行が出ません。画面上部の緑の棒と Up の表示で復旧を確認します。

1回目と2回目のどちらの Pending で Kuma を止めた場合も、復旧後の再停止を試せます。Up に戻ったことを確認したら、`docker compose stop demo` を実行します。復旧後の緑の棒より右を数えます。オレンジの棒2本の間は通知が届かず、最初の赤い棒で Down が確定し、初回通知が届きます。

再通知まで確かめるときは、アプリを停止したまま、再停止後の赤い棒が3本になるまで待ちます。受信ログで、赤い棒の2本目では通知が増えず、3本目で最初の再通知が1件届くことを確認します。最初の Pending から復旧したケースで2回目の再通知まで確かめるときは、赤い棒が5本になるまで待ちます。受信ログで、4本目では通知が増えず、5本目で2回目の再通知が1件届くことを確認します。

確認後は `docker compose start demo` を実行し、Up に戻るまで待ちます。

改訂時に Kuma の公式ソースから起動した試験では、使い捨てのローカル実験アカウントと独立した一時フォルダーを使用しました。

- HTTP の正常・停止・復旧
- HTTP 200 の誤データを Keyword と Json Query で検知
- SQLite ファイルの退避では health が Up、item が 503 / Down

## 学習順と資源観測の追加

利用者の操作 → 通知 → 遅さ → ログ → 容量 → CPU・メモリー → 通信の順へ調整しました。新しい実 Docker 試験は次のコマンドを対象にします。

- demo の `/lab/.state` に対する `df -h` と `df -i`
- demo と kuma を個別に指定した `docker compose stats --no-stream`
- Kuma から demo を調べる `getent hosts`
- 回数3・応答待ち1秒・全体期限5秒を指定した `ping`
- アプリが誤ったデータを返していても、同じ宛先へ ICMP が届くこと

コマンドは試験用プロジェクトの対象だけに限定し、外側の実行にも時間上限を設けます。CPU・メモリーの固定パーセントや空き容量を、環境共通の成功条件にはしません。1回の観察で分かるのは、その時点の対象の値です。継続監視の構築や Windows ホスト全体の検証は対象外です。

コマンド単体試験では出力を差し替え、対象・引数・上限・結果の読み取りを検査します。Docker イメージ内での実行結果は、冒頭の WSL 2 上での確認を参照してください。
